## [Unreleased]

### Added
- `.github/workflows/ci.yml` — GitHub Actions CI that runs the test suite on every push and pull request.
- `CHANGELOG.md` (this file).
- `CONTRIBUTING.md` — contribution guidelines specific to this repository's constraints (zero-breakage philosophy, zero dependencies, agent-agnostic design, test requirements).
- Private-network (SSRF) protection in `tools/seo-tool`: every fetch — the initial requested URL and every redirect hop — is refused by default when its host is a literal RFC1918, link-local/cloud-metadata (`169.254.0.0/16`, including `169.254.169.254`), or equivalent IPv6 (`fe80::/10`, `fc00::/7`, `::`, and IPv4-mapped forms of any of the above) address. `localhost`, `127.0.0.0/8`, and `::1` remain allowed by design, since auditing a local dev server is a documented use case. `--allow-private-network` (`allowPrivateNetwork` option) is a new, explicit, opt-in flag on every fetching command (`crawl`, `page`, `sitemap`, `robots`, `links`, `audit`) for deliberately auditing an internal/LAN target. See `lib/url-utils.js`'s `isPrivateNetworkTarget` and the "Private-network protection" section of `docs/tooling.md`.
- `canonicalCount`, `multipleCanonicals`, and `canonicalRawHrefs` fields on every `page`/`crawl` result: a page can declare more than one `<link rel="canonical">`, which real search engines only honor one of — these surface that ambiguity (with every declared href, unresolved, as evidence) instead of silently showing only the first as if there were no conflict. The human-readable `page` summary flags it on the `Canonical:` line too. See the "canonical-resolution note" in `docs/tooling.md`.
- hreflang extraction: `hreflangTags` (every `<link rel="alternate" hreflang="...">` declaration, href resolved to an absolute URL the same way `canonical` is), `hreflangCount`, `hasXDefault`, `selfReferencingHreflang`, `duplicateHreflangValues`, and `malformedHreflang` fields on every `page`/`crawl` result — surfacing exactly the facts `workflows/international-seo.md` already needs (self-reference/reciprocity setup, `x-default` presence, conflicting duplicate declarations, and the specific mistakes that doc calls out: an underscore instead of a hyphen, and `"xx-UK"` instead of `"xx-GB"`). The human-readable `page` summary shows a `Hreflang:` line when a page declares any. See the "hreflang note" in `docs/tooling.md`.
- `lib/duplicate-content.js` — cross-page duplicate title/meta-description detection for `crawl`/`links`/`audit`: a new `duplicateContent` report section (`duplicateTitles`/`duplicateMetaDescriptions`, each `{ value, urls }` groups, most-duplicated first) makes `checklists/on-page-checklist.md`'s "every indexable page has a unique title/meta description" requirement actually checkable across a real crawled site, instead of requiring a human to eyeball every page. Only genuinely indexable pages are compared — a page marked `indexable: false` (noindex, or a non-200 response with a real body, e.g. a shared custom error page) is excluded, so two 404s sharing a generic title aren't flagged as a false-positive finding. The human-readable `crawl`/`audit` summary shows a duplicate-count line when any exist. See the "duplicate-content note" in `docs/tooling.md`.
- `linkGraph.sitemapIndexabilityConflicts` on `audit`: `{ url, reason }` for every sitemap-listed URL that was also reached and fetched within the crawl but turned out `noindex`, robots-blocked, or a non-200 response — making `checklists/technical-checklist.md`'s "`noindex` and sitemap inclusion never contradict each other" and `checklists/indexing-checklist.md`'s "never leave a sitemap entry for a `noindex`ed, blocked, or non-200 URL" requirements actually checkable. Reuses the same `knownUrls` cross-reference orphan detection already does, and shares the same honest bound: a sitemap URL outside the crawl's reached scope is not reported either way, never assumed clean. The human-readable `audit` summary shows a conflict count. See the "sitemap/indexability conflict note" in `docs/tooling.md`.
- `linkGraph.internalLinksThroughRedirects` on `crawl`/`links`/`audit`: `{ from, to, finalUrl, redirectHops }` for every internal link whose target only resolved after one or more redirect hops — making `checklists/internal-linking-checklist.md`'s "linking to... redirect chains" flag, and `workflows/internal-linking.md`/`workflows/technical-seo.md`'s explicit "fix the link's destination... don't rely on a redirect alone" / "never introduce a new redirect hop to fix an old one" guidance, actually actionable: `finalUrl` is exactly what the link's href should be updated to. A separate, distinct finding from `brokenInternalLinks`/`unverifiedInternalLinks` — the link still works, it just wastes a hop. The human-readable summary shows a count. See the "internal-links-through-redirects note" in `docs/tooling.md`.
- Pagination extraction: `isPaginated`, `paginationNext`, `paginationPrev` (from `<link rel="next"/"prev">`, resolved the same way `canonical`/`hreflang` hrefs are) and `paginationCanonicalConflict` fields on every `page`/`crawl` result. `paginationCanonicalConflict` makes `rules/canonical-rules.md`'s documented anti-pattern actually checkable: "canonicalizing all pages to page 1 is usually wrong" — it's `true` exactly when a paginated page's canonical points to a different URL than itself, instead of the correct self-referencing canonical. The human-readable `page` summary shows a `Pagination:` line when a page is actually paginated. See the "pagination note" in `docs/tooling.md`.
- `lib/report-diff.js` and a new `diff <report1.json> <report2.json>` command: compares two previously-saved `--json=path` report files, making `workflows/monitoring.md`'s "establish a full baseline snapshot first" and `workflows/post-implementation.md`'s "log the change for future comparison" actually actionable instead of requiring a human to diff two JSON files by eye. Pages are matched between reports by normalized URL (never by array order), and reported as added/removed/changed across a bounded, SEO-meaningful field set (`status`, `indexable`, `canonical`, `multipleCanonicals`, `title`, `metaDescription`, `robotsMetaDirectives`, `xRobotsTagDirectives`, `robotsDirectivesConflict`, `h1Count`, `isPaginated`, `paginationCanonicalConflict`); `linkGraph`/`duplicateContent` findings are diffed the same way, section-by-section, and reported as `null` (not guessed) when either report lacks that section. `regressions`/`improvements` are populated from exactly one signal — a page's `indexable` flipping `true → false` or `false → true` — the one transition `workflows/monitoring.md` itself calls out as confident enough to classify; every other tracked-field difference is reported as a plain, unjudged `changed` entry. An invalid, missing, or non-seo-tool report file produces a clear error and exit 1, not a crash. See the "report-diff note" in `docs/tooling.md`.
- `robotsDirectivesConflict` and `robotsDirectivesConflictReasons` fields on every `page`/`crawl` result: `checklists/metadata-checklist.md` requires "no conflicting robots directives between meta tag and HTTP header" — a page's `<meta name="robots">` and its `X-Robots-Tag` HTTP header are two independent mechanisms that can disagree (e.g. a CDN adding a blanket `X-Robots-Tag: noindex` while the template still declares `index, follow`). `robotsDirectivesConflict` is `true` exactly when the two sources assert opposite values for the same directive family (`index`/`noindex` or `follow`/`nofollow`, with the `all`/`none` shorthand expanded first) — a directive present in only one source is correctly not flagged, since there's nothing to disagree with. This is a separate, additive fact and never changes the existing `indexable` signal, which already treats a `noindex` from either source as authoritative. The human-readable `page` summary's new `X-Robots-Tag:` line shows a `CONFLICT:` marker with the reason when one exists. See the "robots-directives-conflict note" in `docs/tooling.md`.
- `missingRequiredProperties` field on every JSON-LD block in `jsonLd` (`page`/`crawl` results): `checklists/schema-checklist.md` requires "Required properties for the chosen type present (`@context`, `@type`, and type-specific required fields)" — this checks the two universal, spec-level properties (`@context`, `@type`) every JSON-LD/schema.org block needs, correctly handling the `@graph` container pattern (no `@type` expected on the container itself) and a top-level JSON-LD array (checked item-by-item, results deduplicated). `null` instead of an empty array when the block's JSON never parsed, so "not evaluated" is never confused with "checked, nothing missing." Deliberately does *not* validate type-specific required fields (`Article` needs `datePublished`, `Product` needs `offers`, etc.) — that would mean building and maintaining a database of schema.org's hundreds of types, an unnecessarily broad validator this tool does not attempt; that judgment stays with `rules/schema-rules.md` and `rules/no-fabrication.md`. The human-readable `page` summary's `JSON-LD blocks:` line shows a missing-property count when applicable. See the "JSON-LD required-properties note" in `docs/tooling.md`.
- `lib/hreflang-reciprocity.js` — cross-page hreflang reciprocity detection for `crawl`/`links`/`audit`: a new `hreflangReciprocity` report section (`nonReciprocalHreflang`, `{ from, to, hreflang }` entries) makes `checklists/international-seo-checklist.md`'s "Every language/region variant has a complete, reciprocal hreflang set (every page links to every variant, including itself)" requirement actually checkable across a real crawled site — `lib/html-extract.js`'s per-page `extractHreflang` explicitly could not check this alone, since it needs the whole crawled set. Only a declared hreflang target that was also reached and fetched within the same crawl can be checked (the same honest bound `orphanCandidates`/`sitemapIndexabilityConflicts` already use) — a target outside the crawl's reached scope is never reported either way, and a self-referencing declaration is correctly not a reciprocity concern. The human-readable `crawl`/`audit` summary shows a non-reciprocal count when any are found, and the new section is diffed by `diff` the same way `linkGraph`/`duplicateContent` already are. See the "hreflang-reciprocity note" in `docs/tooling.md`.
- `width`, `height`, `hasExplicitDimensions`, and `loading` fields on every entry in `images` (`page`/`crawl` results), plus a new page-level `imagesMissingDimensions` count: `checklists/performance-checklist.md` and `workflows/performance.md` both name "images/embeds without explicit dimensions" as a concrete Cumulative Layout Shift (CLS) risk factor, with `width`/`height` (or `aspect-ratio`) and `loading="lazy"` named as the documented attribute-level fix. `hasExplicitDimensions` is `true` when both `width` and `height` HTML attributes are present, or an inline `style` attribute declares `aspect-ratio` (the documented alternative — inline-style only, not a full CSS parser). `loading` is captured as a raw fact only, never judged — whether a specific image should be lazy-loaded depends on its position on the rendered page, which this static-HTML tool can't determine; that stays a reasoning-layer judgment. The human-readable `page` summary's existing `Images missing alt:` line now also shows `Images missing dimensions:`. See the "image-dimensions note" in `docs/tooling.md`.
- `ogUrlCanonicalMismatch` field on every `page`/`crawl` result: `checklists/metadata-checklist.md` requires "`og:url` — matches canonical" — `og:url` and `<link rel="canonical">` are two independent signals for a page's one true URL that can drift apart (a stale `og:url` left over from a URL-structure change, or a canonical rewrite that never touched the Open Graph tags). `true` exactly when both are present and, once `og:url` is resolved to an absolute URL the same way every other href in this tool is, they disagree — a fragment-only difference doesn't count, mirroring the existing `paginationCanonicalConflict` convention. A missing `og:url` or a missing `canonical` is correctly not flagged, since a missing canonical is already its own, separately-reported problem. The human-readable `page` summary shows a `MISMATCH:` line when this fires, and the field is tracked by `diff` the same way `robotsDirectivesConflict`/`paginationCanonicalConflict` already are. See the "og-url-canonical note" in `docs/tooling.md`.

### Fixed
- `canonical` is now always resolved to an absolute URL against the page's real, post-redirect URL, the same as `internalLinks`/`externalLinks`/`images` already were. ## [1.0.0] — 2026-08-27

Initial stable release of the SEO Toolkit.

### Added
- The core SEO engineering skill: `SKILL.md` (agent-agnostic controller), `rules/`, `workflows/`, `checklists/`, `frameworks/`, `templates/`, and `commands/` — a reusable, evidence-driven SEO engineering system for any AI coding agent.
- `docs/` — installation, usage, architecture, safety, workflow, and tooling reference documentation.
- `tools/seo-tool` — a zero-dependency, read-only Node.js CLI for local SEO inspection: `crawl`, `page`, `links`, `sitemap`, `robots`, `audit`, and `project` commands, producing structured JSON evidence for the reasoning layer to consume.
- `README.md`'s Architecture section and Mermaid diagram describing the knowledge-layer / fact-gathering-layer split and the `AUDIT → PLAN → RISK CHECK → FIX → VERIFY → REPORT` loop.
- `README.md`'s "External SEO Work" section, documenting the SEO work that genuinely requires external platforms, external data, or business input (Search Console, analytics, keyword/backlink tools, competitor SERP data, Google Business Profile, business context, external infrastructure).
- MIT `LICENSE`.

### Improved (reliability & test infrastructure)
- Added dedicated test coverage for `cli.js` (command dispatch, argument parsing, exit codes, `--json`/`--json=path` output), `lib/fetch-utils.js` (timeouts, redirect chains, redirect loops, capped body reads, network-error classification), and `lib/report.js` (the documented JSON report schema) — none of these had direct test coverage before.
- Added `<sitemapindex>` recursion: `sitemap` and `audit` now resolve the full tree of child sitemaps by default — bounded (`--max-sitemaps`, `--max-sitemap-depth`), same-origin restricted, duplicate/cycle-protected, and never aborting the whole tree on one malformed or unreachable child. This fixed a real bug where `audit`'s orphan-page detection silently produced empty results against any site whose sitemap was an index rather than a single `<urlset>`.
- Fixed a Windows-specific bug where a local file path (e.g. `D:\path\to\sitemap.xml`) passed to the sitemap resolver was misparsed as a URL with a one-letter scheme, which would have incorrectly rejected every child sitemap as "cross-origin."
- Test suite grew from 69 to 132 tests as part of this work, all passing.
- Updated `docs/safety.md` to reflect the authoritative Category A/B/C/D risk model already in use in `SKILL.md` and `rules/implementation-safety.md`.
- Cleaned up minor review findings: removed a dead conditional in the sitemap CLI summary, replaced an ambiguous `entryCount` field (which meant different units for `urlset` vs. `sitemapindex` nodes) with clearly-named `urlCount`/`childCount` fields, removed an unused internal field, and documented the bounded worst-case latency of sequential sitemap-index processing.
