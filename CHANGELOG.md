## [Unreleased]

### Added
- `.github/workflows/ci.yml` — GitHub Actions CI that runs the test suite on every push and pull request.
- `CHANGELOG.md` (this file).
- `CONTRIBUTING.md` — contribution guidelines specific to this repository's constraints (zero-breakage philosophy, zero dependencies, agent-agnostic design, test requirements).
- Private-network (SSRF) protection in `tools/seo-tool`: every fetch — the initial requested URL and every redirect hop — is refused by default when its host is a literal RFC1918, link-local/cloud-metadata (`169.254.0.0/16`, including `169.254.169.254`), or equivalent IPv6 (`fe80::/10`, `fc00::/7`, `::`, and IPv4-mapped forms of any of the above) address. `localhost`, `127.0.0.0/8`, and `::1` remain allowed by design, since auditing a local dev server is a documented use case. `--allow-private-network` (`allowPrivateNetwork` option) is a new, explicit, opt-in flag on every fetching command (`crawl`, `page`, `sitemap`, `robots`, `links`, `audit`) for deliberately auditing an internal/LAN target. See `lib/url-utils.js`'s `isPrivateNetworkTarget` and the "Private-network protection" section of `docs/tooling.md`.
- `canonicalCount`, `multipleCanonicals`, and `canonicalRawHrefs` fields on every `page`/`crawl` result: a page can declare more than one `<link rel="canonical">`, which real search engines only honor one of — these surface that ambiguity (with every declared href, unresolved, as evidence) instead of silently showing only the first as if there were no conflict. The human-readable `page` summary flags it on the `Canonical:` line too. See the "canonical-resolution note" in `docs/tooling.md`.
- hreflang extraction: `hreflangTags` (every `<link rel="alternate" hreflang="...">` declaration, href resolved to an absolute URL the same way `canonical` is), `hreflangCount`, `hasXDefault`, `selfReferencingHreflang`, `duplicateHreflangValues`, and `malformedHreflang` fields on every `page`/`crawl` result — surfacing exactly the facts `workflows/international-seo.md` already needs (self-reference/reciprocity setup, `x-default` presence, conflicting duplicate declarations, and the specific mistakes that doc calls out: an underscore instead of a hyphen, and `"xx-UK"` instead of `"xx-GB"`). The human-readable `page` summary shows a `Hreflang:` line when a page declares any. See the "hreflang note" in `docs/tooling.md`.
- `lib/duplicate-content.js` — cross-page duplicate title/meta-description detection for `crawl`/`links`/`audit`: a new `duplicateContent` report section (`duplicateTitles`/`duplicateMetaDescriptions`, each `{ value, urls }` groups, most-duplicated first) makes `checklists/on-page-checklist.md`'s "every indexable page has a unique title/meta description" requirement actually checkable across a real crawled site, instead of requiring a human to eyeball every page. Only genuinely indexable pages are compared — a page marked `indexable: false` (noindex, or a non-200 response with a real body, e.g. a shared custom error page) is excluded, so two 404s sharing a generic title aren't flagged as a false-positive finding. The human-readable `crawl`/`audit` summary shows a duplicate-count line when any exist. See the "duplicate-content note" in `docs/tooling.md`.
- `linkGraph.sitemapIndexabilityConflicts` on `audit`: `{ url, reason }` for every sitemap-listed URL that was also reached and fetched within the crawl but turned out `noindex`, robots-blocked, or a non-200 response — making `checklists/technical-checklist.md`'s "`noindex` and sitemap inclusion never contradict each other" and `checklists/indexing-checklist.md`'s "never leave a sitemap entry for a `noindex`ed, blocked, or non-200 URL" requirements actually checkable. Reuses the same `knownUrls` cross-reference orphan detection already does, and shares the same honest bound: a sitemap URL outside the crawl's reached scope is not reported either way, never assumed clean. The human-readable `audit` summary shows a conflict count. See the "sitemap/indexability conflict note" in `docs/tooling.md`.
- `linkGraph.internalLinksThroughRedirects` on `crawl`/`links`/`audit`: `{ from, to, finalUrl, redirectHops }` for every internal link whose target only resolved after one or more redirect hops — making `checklists/internal-linking-checklist.md`'s "linking to... redirect chains" flag, and `workflows/internal-linking.md`/`workflows/technical-seo.md`'s explicit "fix the link's destination... don't rely on a redirect alone" / "never introduce a new redirect hop to fix an old one" guidance, actually actionable: `finalUrl` is exactly what the link's href should be updated to. A separate, distinct finding from `brokenInternalLinks`/`unverifiedInternalLinks` — the link still works, it just wastes a hop. The human-readable summary shows a count. See the "internal-links-through-redirects note" in `docs/tooling.md`.

### Fixed
- `canonical` is now always resolved to an absolute URL against the page's real, post-redirect URL, the same as `internalLinks`/`externalLinks`/`images` already were. Previously a relative or root-relative canonical href (e.g. `/widgets`) was returned exactly as written in the markup, unresolved — usable for a same-page string comparison but not as an actual URL.

## [1.0.0] — 2026-08-27

Initial stable release of the SEO Toolkit.

### Added
- The core SEO engineering skill: `SKILL.md` (agent-agnostic controller), `rules/`, `workflows/`, `checklists/`, `frameworks/`, `templates/`, and `commands/` — a reusable, evidence-driven SEO engineering system for any AI coding agent.
- `docs/` — installation, usage, architecture, safety, workflow, and tooling reference documentation.
- `tools/seo-tool` — a zero-dependency, read-only Node.js CLI for local SEO inspection: `crawl`, `page`, `links`, `sitemap`, `robots`, `audit`, and `project` commands, producing structured JSON evidence for the reasoning layer to consume.
- `README.md`'s Architecture section and Mermaid diagram describing the knowledge-layer / fact-gathering-layer split and the `AUDIT → PLAN → RISK CHECK → FIX → VERIFY → REPORT` loop.
- `README.md`'s "External SEO Work" section, documenting the SEO work that genuinely requires external platforms, external data, or business input (Search Console, analytics, keyword/backlink tools, competitor SERP data, Google Business Profile, business context, external infrastructure).
- MIT `LICENSE`.

### Improved (reliability & test infrastructure)
- Added dedicated test coverage for `cli.js` (command dispatch, argument parsing, exit codes, `--json`/`--json=path` output), `lib/fetch-utils.js` (timeouts, redirect chains, redirect loops, capped body reads, network-error classification), and `lib/report.js` (the documented JSON report schema) — none of these had direct test coverage before.
- Added `<sitemapindex>` recursion: `sitemap` and `audit` now resolve the full tree of child sitemaps by default — bounded (`--max-sitemaps`, `--max-sitemap-depth`), same-origin restricted, duplicate/cycle-protected, and never aborting the whole tree on one malformed or unreachable child. This fixed a real bug where `audit`'s orphan-page detection silently produced empty results against any site whose sitemap was an index rather than a single `<urlset>`.
- Fixed a Windows-specific bug where a local file path (e.g. `D:\path\to\sitemap.xml`) passed to the sitemap resolver was misparsed as a URL with a one-letter scheme, which would have incorrectly rejected every child sitemap as "cross-origin."
- Test suite grew from 69 to 132 tests as part of this work, all passing.
- Updated `docs/safety.md` to reflect the authoritative Category A/B/C/D risk model already in use in `SKILL.md` and `rules/implementation-safety.md`.
- Cleaned up minor review findings: removed a dead conditional in the sitemap CLI summary, replaced an ambiguous `entryCount` field (which meant different units for `urlset` vs. `sitemapindex` nodes) with clearly-named `urlCount`/`childCount` fields, removed an unused internal field, and documented the bounded worst-case latency of sequential sitemap-index processing.
